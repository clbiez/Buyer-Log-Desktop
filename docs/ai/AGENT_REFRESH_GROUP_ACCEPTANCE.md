# Native refresh-group definitions for agents

Four Office tools adapt the existing shared refresh-group definitions: `source.refreshgroups.read` and approved `source.refreshgroup.create`, `.update` and `.delete`. Groups are stored in the native SETTINGS document through `refresh-group-service.js` under the native SETTINGS lease and section revision. The existing data-domain rules (`refreshableModules`, linked-module normalization, MAX_GROUPS, unique case-insensitive names) are the only business logic; no second rule set exists. Tools report `executesRefresh:false`: definitions are managed, refresh execution remains the user's own refresh workflow and is a separate pending packet.

Writes require current `source` area plus `manageModelConnections`, are re-checked at every critical await through the Office authority guard and the HTTP route, archive the complete prior definitions in the existing framed owner/tool/task/step-bound inverse service, and verify read-back after commit. Inverse refuses newer peer revisions (fingerprint/revision bound). Legacy stored metadata that native normalization would drop is reported by READ (`legacyNormalizationRequired`) and blocks Office writes instead of being silently erased. The HTTP PUT route now uses the same lease/readback service and rejects inputs that native normalization would silently drop (for example duplicate group IDs).

Root cause of the WIP failure: the fail-closed tool schema validator advertised but ignored `uniqueItems`, so `moduleIds:['cp','cp']` passed the schema. `agent-tool-schema.js` now enforces `uniqueItems`; this also makes the existing checklist `orderKeys` contracts enforce what they declared. The safety assertion was not loosened.

Validation: refresh-group capability 13 cases plus a schema unit case pass; the agent/checklist/refresh test groups (68 files, 971 cases) pass with zero failures. Actual anonymous HTTP/Chromium acceptance on an isolated server uses the real username/password form: execution without approval returns 409 OFFICE_APPROVAL_REQUIRED, approved create persists revision 1 with linked modules, the real Office "Undo this step" dialog restores the empty list at revision 2, both UI languages are verified and there are zero page errors. ## Refresh-group execution

`source.refreshgroup.execute` (EXECUTE, approval) runs the current owner's existing asynchronous model refresh for the group's native targets. `/api/refresh` and the tool share one native start (`startNativeRefresh`); the targets come from the stored definition through the same `refreshTargetsFor` linked-module rules, and the source-filter readiness check now evaluates the actual user profile in both paths. The preview reports targets, filter readiness, any running refresh and `rollback: unavailable` (a refresh replaces only the owner's snapshot; no inverse is offered). Apply re-reads the definition under the Office profile guard and refuses changed targets, a missing filter or a running refresh; the Office job/step command key makes a replay return the same native job instead of starting a second refresh; a replay while its own job is still running fails safely on the changed approval fingerprint (no second refresh). The step waits as `waiting_operation`; poll completes only from the matching native job's `done` state and fails a superseded, cancelled or failed job.

Limits: native refresh jobs are process memory, so a server restart during a refresh makes the next poll fail the step (no blind restart). Validation: 16 refresh-group capability cases (three new execute cases with the native job contract), 43 refresh/agent contract files and the access matrix pass. Actual anonymous HTTP/Chromium: approval required (409 without it), approved execution started a real native refresh job, and on the demo server without an ASAS source that job ended in error and the poll marked the step failed (`OFFICE_NATIVE_OPERATION_FAILED`); TR/EN, zero page errors. A real configured-source completion is not claimed.
